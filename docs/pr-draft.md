# Draft: Align mobile GPUI types and make native iOS rendering work

Align gpui/gpui_wgpu with Ely/patch-map's Zed `1a28cff4b409169bac058bca40dfbfeb7621d19b` and crates.io wgpu `29.0.4`. Adapt platform, dispatcher, atlas and display APIs; match the example's reqwest source to avoid duplicate Client types. Core gpui-mobile stays independent of Ely, while the app-layer example supplies Ely assets. Application lockfiles preserve the tested libc resolution and TLS certificate validation remains enabled.

Fix two causes of a linked iOS app opening to a black screen: provide wgpu's Metal display handle and retain `run_embedded()`'s application handle while UIKit owns the run loop. Propagate renderer failures and provide a POSIX native simulator build path. The integrated scope also includes raw touch/pinch/lifecycle/inset contracts, asynchronous GPS, and opt-in BLE scan/connect/discover/read/write/notify/disconnect/reconnect with Android Java packaging.

Validation: the GPUI showcase compiled, linked, installed and visibly rendered on iPhone 17 Pro / iOS 26.3. The latest iOS Rc/Weak backend and Ely app also compiled and linked (3m56s), launched as PID 18809 at 21:28 KST, and executed both `ELY_FLOATING_KEYBOARD_SELFCHECK PASS` and `ELY_ADAPTER_SELFCHECK PASS` (`native-ios-keyboard-final.log`, `runtime-ios-keyboard-final.log`); `ely-viewport-keyboard-ready.png` shows controls and canvas. All 13 real-GPUI simulator event/ownership/text/FIFO tests passed. Android root and example checks passed with BLE; the latest shared source compiled and linked as an ARM64 cdylib (26.07s). The BLE-enabled debug APK assembled successfully (1m02s), its signature verified, and its packaged native-library hash matches that cdylib. Dependency trees show one GPUI revision and one wgpu. See the compatibility matrix for artifact hashes and source identity.

The separate Ely Android app now has a NativeActivity host and APK build path. With Ely `7f6a3f91` and the same GPUI/wgpu pins, its cdylib compiled and linked in 26.60s and JDK 21 Gradle packaging succeeded in 32s (`ely-integration-evidence/android-apk-final.log`). The final artifact is `outputs/ely-integration-arm64-debug.apk`, independently of the BLE APK. The builder verified its `dev.gpui.mobile.ely` identity, `Ely Integration` label, ARM64 native library, JNI/NativeActivity exports and v2 debug signature; the checksum is recorded in the compatibility matrix, with independent SHA-256 and apksigner v2 signature verification passed. The Ely app also uses painted input bounds and reveal helpers to avoid floating keyboards; only full-width docked keyboards contribute bottom occlusion, combined with safe area using `max`. Full control-area occlusion remains a limitation. Both keyboard and adapter assertions passed in the final iOS simulator run; this does not establish actual gesture or keyboard interaction.

Android execution, real GPS/BLE radio behavior, full surface recovery and FPS are not verified. No Android targets were connected and the SDK emulator executable is absent. Actual click/drag/pinch and keyboard interaction were not performed because the Mac was locked; its UI was untouched. System-power sleep/wake is unsupported; Android idle inhibition explicitly errors. Some simulator emoji glyphs are missing. See [compatibility](compatibility.md), [mobile events](mobile-events.md), [location](location-service-integration.md), and [BLE](ble-integration.md) for evidence and platform constraints.
